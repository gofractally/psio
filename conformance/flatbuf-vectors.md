# FlatBuffers fixture

`flatbuf-vectors.json` pins **the FlatBuffers bytes of known values**, and a
set of buffers a verifier must refuse. It is generated by
`psio_flatbuf_conformance_emit` (`cpp/tests/flatbuf_conformance_emit.cpp`,
from the declarations and values in `cpp/tests/flatbuf_shapes.hpp`); the
ctest `psio_flatbuf_conformance_regen` fails if the checked-in file is not
what the C++ implementation generates. Regenerate with

```sh
<build>/cpp/tests/psio_flatbuf_conformance_emit conformance/flatbuf-vectors.json
```

The schema of the types is `cpp/tests/flatbuf/interop.fbs` (`Numbers`,
`Entry`, `Basket`, `Longs`, `Sparse` are declared in `flatbuf_shapes.hpp`
only). The Rust declarations are `rust/psio/tests/flatbuf_shapes/mod.rs`.

## What the bytes are

They are what `psio::to_flatbuf` writes, and — for every value that
`cpp/tests/flatbuf_interop_tests.cpp` also builds through the official
library (`Order`, `Tree`, `Scalars`, `Defaults`, `Renumbered`,
`WithDeprecated`) — byte for byte what the official object API
(`T::Pack` + `FlatBufferBuilder::Finish`, FlatBuffers 25.12.19) writes:
fields in `flatc`'s order (by size, largest first; within a size by
descending field id), children written before their table in field order,
identical vtables shared, a scalar equal to its default and an empty
string / vector not written.

## Rows

Version 2 (version 1 had no `accept_corrupt` and `mutation_digests`
sections, no `at`, and no options on rejected rows).

`accept`: `{id, type, wire_hex}`, plus `file_identifier` (the four
characters after the root offset) and / or `size_prefixed: true` (the
buffer starts with its 32-bit size) where the buffer was written with them.
The value of a row is the one its `id` names in `flatbuf_shapes.hpp` /
`flatbuf_conformance_emit.cpp`; a consumer declares the same types and
values and checks decode (bytes to value) and encode (value to the same
bytes).

`reject`: `{id, type, error, at, wire_hex}`, plus `file_identifier` /
`size_prefixed` where the verifier is asked for them: a buffer
`validate_flatbuf<type>` refuses, the message C++ refuses it with and the
position it reports. Two kinds:

* written by hand, one for each reason the verifier has (the rows whose id
  names the reason: `Profile/null_root`, `Order/union_none_with_value`,
  `Tree/shared_subobjects`, `Basket/shared_string`,
  `Order/shared_key_bytes`, …). Every message of `validate_flatbuf` is
  there except the three that cannot be reached or stored: "buffer larger
  than 2 GiB", "field out of bounds" and "table out of bounds" (the checks
  before them already cover the buffer);
* `<type>/mutated_NNN`: deterministic corruptions (one or two edits of a
  byte, a 16-bit word, a 32-bit word, or a truncation; splitmix64, so the
  rows are the same on every platform) of `Profile/sample`, `Tree/nested`,
  `Basket/full`, `Order/compact` and a `Longs`, with the verdict of the C++
  verifier.

`accept_corrupt`: `{id, type, wire_hex}`: a buffer that is not the encoding
of an intended value and that the verifier accepts all the same —
`<type>/mutated_valid_NNN`, the corruptions above that stay structurally
valid (a changed scalar, a changed padding byte, an offset that lands on
another valid object), and two rows written to show where a language with
stricter types than C++ differs:

* `Profile/name_not_utf8`: a FlatBuffers string is bytes; C++ `std::string`
  holds them;
* `Order/color_out_of_range`: an enum is its underlying integer; a C++ enum
  holds any value of it.

A consumer accepts these rows, and what it decodes re-encodes to a buffer
that validates.

`mutation_digests`: `{type, base, seed, count, accepted, digest}`: the
verdicts of the verifier on `count` corruptions of the accepted row `base`,
as one number. The corruptions are drawn as for the `mutated` rows
(`corrupt` in the emitter: splitmix64 seeded with `seed`; one or two edits;
an edit is a position `next % size` and then, by `next % 6`: a byte set to
`next`; a byte plus 4; one bit `next % 8` flipped; the aligned 32-bit word
set to `next % (size + 8)` when `next % 2`, else to `next`; the aligned
16-bit word set to `next % 96`; a truncation at the position). The digest
is FNV-1a (64-bit) over, per buffer: the byte 1 when it is accepted; else
the byte 0, the message, and the position as 4 bytes, little-endian.
`accepted` counts the accepted ones. A consumer that draws the same
corruptions and arrives at the same number agrees on every verdict, reason
and position: 300,000 buffers over ten rows.

Together the `reject`, `accept_corrupt` and `mutation_digests` rows pin the
accepted set: the same bytes get the same answer, for the same reason, in
every language.

## Consumers

| Language | Accepted rows | Rejected rows | Corrupted rows C++ accepts | Digests |
|---|---|---|---|---|
| C++ | all 27: validated, decoded, viewed, re-encoded (the emitter aborts otherwise; `--check` in ctest) | all 429 refused with the stated message at the stated position | all 62 accepted; the decoded value re-encodes to a valid buffer | computed by the emitter |
| Rust (`rust/psio/tests/flatbuf_conformance.rs`) | all 27, for two sets of declarations (below): decoded (checked, trusted, through the view) to the value and re-encoded to the same bytes | all 429 refused; with the `raw` declarations for the same reason at the same position | all 62 accepted with the `raw` declarations; with the `natural` ones 53 accepted and 9 refused, each for one of the two reasons below | all ten reproduced with the `raw` declarations: 300,000 buffers, 82,459 accepted; with the `natural` ones every buffer C++ refuses is refused and an accepted one is refused only for the two reasons below |
| JavaScript, Python | none: neither package implements FlatBuffers | none | none | none |

Rust declares the types twice. `raw` holds what the C++ types hold:
`RawString` members (any bytes) and an enum with a `#[psio(other)]`
catch-all (any value). Its verifier gives the C++ answer on every row.
`natural` is how a Rust program writes them — `String` and a plain `enum` —
and for those the Rust verifier refuses two things C++ accepts, because the
Rust type cannot hold them: a string that is not UTF-8 (`flatbuf: string is
not valid UTF-8`) and an enum value that is not an enumerator (`flatbuf:
unknown enum value`). In 2 rejected rows one of these checks comes before
the reason C++ gives (`Order/mutated_011`, `Order/mutated_173`); the test
pins both lists.
