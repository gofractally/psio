# pjson conformance corpus

Shared cross-language test fixtures. Both the C++ and Rust
implementations consume the same files here and must produce
byte-identical results.

## Fixture format

Each fixture is a JSON file at `conformance/fixtures/<id>.json` with
the following shape:

```json
{
  "id": "uint_inline_5",
  "spec_ref": "§4.3",
  "rule_ids": ["UI-001", "UI-002"],
  "description": "uint_inline encodes value 5 as the single byte 0x25",

  "input_value": {"kind": "uint", "value": 5},
  "wire_hex": "25",
  "json_compact": "5",

  "must_round_trip": true,
  "must_validate": true
}
```

Field reference:

- `id` — stable identifier, lowercase snake_case, unique across all
  fixtures.
- `spec_ref` — the spec section that pins this rule (e.g. `§4.3`).
- `rule_ids` — list of compliance-matrix row IDs (e.g. `UI-001`) this
  fixture exercises. Many fixtures touch multiple rows.
- `description` — one-line plain-English summary.
- `input_value` — structured representation of the value, in the small
  DSL described below.
- `wire_hex` — the canonical pjson byte sequence as a lowercase hex
  string, no separators. (`"25"` = a single byte 0x25.)
- `json_compact` — the JSON text that decoding `wire_hex` and rendering
  with default emitter options should produce.
- `must_round_trip` — if `true`, the harness checks that
  `encode(input_value) == wire_hex` AND `decode(wire_hex) == input_value`.
  If `false`, only the decode direction is checked (used for fixtures
  that exercise non-canonical encodings the encoder would not produce).
- `must_validate` — if `true`, the strict validator on `wire_hex` must
  pass. If `false`, the buffer is structurally valid but fails some
  canonicality check.

Optional fields for specialized fixtures:

- `json_pretty` — JSON text with the default pretty-print options (indent=2).
- `json_int_string_large_only` — JSON text with `int_string_mode=LargeOnly`.
- `json_int_string_all` — JSON text with `int_string_mode=All`.
- `must_reject` — if `true`, decoder MUST reject `wire_hex` (see
  `fixtures-reject/` for these cases). `wire_hex` is still required.
- `reject_reason` — short string identifier for the expected error
  class (`"truncated"`, `"reserved_tag"`, `"hash_mismatch"`, etc).

## Input-value DSL

`input_value` is structured so both C++ and Rust harnesses can
construct the same `Value` tree without depending on each other's
internal types.

### Atoms

```json
{"kind": "null"}
{"kind": "bool", "value": true}
{"kind": "uint", "value": 5}                 // any non-negative integer
{"kind": "int", "value": -42}                 // signed; encoder picks form
{"kind": "uint128", "lo": "0x...", "hi": "0x..."}
{"kind": "negint128", "lo": "0x...", "hi": "0x..."}
{"kind": "float", "width": 64, "bits_hex": "0x4008000000000000"}
{"kind": "decimal", "mantissa": "12345", "scale": -2}
{"kind": "string", "encoding": "raw_text", "text": "hello"}
{"kind": "string", "encoding": "escape_form", "text": "hello"}
{"kind": "bytes", "encoding": "base64", "bytes_hex": "deadbeef"}
{"kind": "extension", "subtype": 0, "bytes_hex": "..."}
```

### Wrappers

```json
{"kind": "numeric_string", "inner": {"kind": "uint", "value": 123}}
```

### Containers

```json
{"kind": "array", "children": [{...}, {...}]}
{"kind": "typed_array", "element_code": 6, "elements": [1, 2, 3, 4]}
{"kind": "object", "fields": [{"key": "a", "value": {...}},
                              {"key": "b", "value": {...}}]}
{"kind": "row_array", "shape": ["x", "y"], "rows": [[{...}, {...}], ...]}
```

The `value` field in object entries and the `inner` field in
`numeric_string` recursively use the same DSL.

## Directory layout

```
conformance/
├── README.md                    (this file)
├── fixtures/                    (positive cases — must round-trip)
│   ├── 4.1_null/
│   │   └── null.json
│   ├── 4.2_bool/
│   │   ├── false.json
│   │   └── true.json
│   ├── 4.3_uint_inline/
│   │   └── ...
│   ...
└── fixtures-reject/             (negative cases — must reject)
    ├── 4.4_nint_inline_zero.json
    ├── 4.6_ieee_reserved_bit3.json
    └── ...
```

Sub-directories under `fixtures/` mirror the spec section numbers so
a contributor can find every fixture for a section quickly.

## Running the corpus

```sh
tools/run-conformance.sh --lang cpp     # run all fixtures through C++
tools/run-conformance.sh --lang rust    # run all fixtures through Rust
tools/run-conformance.sh                # run both, plus cross-validation
```

The harness exits non-zero on any mismatch (wire-bytes, JSON,
decoded value, or rejection-status mismatch).

## Schema IR text fixture

`schema-json-vectors.json` is separate from the pjson corpus above: it pins
the three serialized forms of the Schema IR (`psio::Schema`) — PSSZ bytes,
`psio::json` text and `psio::ijson` text — for C++, Rust and JavaScript
(`docs/json.md`, "The Schema IR as JSON"). It is generated by
`psio_schema_json_conformance_emit`
(`cpp/tests/schema_json_conformance_emit.cpp`); the ctest
`psio_schema_json_conformance_regen` fails if the checked-in file is not what
the C++ implementation generates. Consumed by
`cpp/tests/schema_json_conformance_tests.cpp`,
`rust/psio/tests/schema_json_conformance.rs` and
`js/src/test/schema-json-conformance.test.ts`.

```
{ "version": 1,
  "schemas": [ { "name", "ir_hex", "json", "ijson" } ],
  "accepts": [ { "name", "format", "text", "ir_hex" } ],
  "rejects": [ { "name", "format", "text" } ] }
```

`ir_hex` is the lowercase hex of `pssz(Schema)`; `json`, `ijson` and `text`
are whole documents held in a JSON string; `format` is `"json"` or
`"ijson"`.

| rows | every language must |
|---|---|
| `schemas` | decode `ir_hex` and write exactly `json` and `ijson`; read each text and encode exactly `ir_hex` |
| `accepts` | read `text` under `format` (it is not canonical: reordered members, unknown or repeated keys, an absent `ir_version`, a small 64-bit integer as a string, ...) and encode exactly `ir_hex` |
| `rejects` | reject `text` under `format` |

The schemas are `pssz-vectors`, `json-vectors` and `time-key-vectors` (the
`schema_ir` of those fixtures, built by the same code), `schema-of-schema`
(the IR of `psio::Schema` itself), `empty`, `every-alternative` (written by
hand: all 15 alternatives, attributes, a package, interfaces, worlds, uses,
64-bit integers on both sides of 2^53 - 1, no `ir_version`; it is data for
the IR's codecs, not a schema to encode values with) and
`lists-nested-to-the-limit` (the deepest inline nesting the readers' limit
of 64 allows).

## Nested values in the shared codec fixtures

`pssz-vectors.json` and `time-key-vectors.json` are described in
`pssz-vectors.md` and `time-key-vectors.md`. `json-vectors.json` (emitted by
`cpp/tests/json_conformance_emit.cpp`; type ids and row kinds in
`cpp/tests/json_conformance_types.hpp`) holds these nested-value types
(`docs/json.md`, "Nested values"; Schema IR node `Nested`):

| type id | type |
|---|---|
| `NestedArgs` | `record{to: string, amount: u64, memo: optional<string>}` — the inner record |
| `nested<u64>` | a nested `u64`: its text is the integer's (a string beyond 2^53 − 1 under ijson) |
| `nested<NestedArgs>` | a nested record: its text is the record's object |
| `nested<NestedArgs,deferred>` | the same with deferred validation: same text, bytes and IR |
| `optional<nested<u64>>`, `list<nested<NestedArgs>>` | in an optional, as list elements |
| `NestedChoice` | `variant<u32, nested<NestedArgs>>`: the ijson alternative name is `nested_NestedArgs` |
| `NestedAction` | `record{method: u32, args: nested<NestedArgs>, twice: nested<nested<u64>>, maybe: optional<nested<NestedArgs>>, many: list<nested<u64>>}` |
| `map<string,nested<NestedArgs>>` | nested mapped values: an object whose members are the inner records' objects |
| `set<nested<u64>>` | nested elements: the array of the inner integers, in the order of their inner **bytes** (256 before 1) |
| `map<nested<u64>,u8>` | a nested key is not a string by type: the array of `[k, v]` pairs, in the same order |
| `nested<map<string,u32>>` | a map inside nested bytes: the map's own object |

Their rows are the ordinary kinds: `value` (both texts and the `pssz` bytes,
which are those of the byte list holding the inner encoding), `accept` (a
non-canonical inner text — member order, unknown or repeated members, a
missing optional member, an integer in its other form — reads as the value
whose canonical text is `canonical`) and `reject` (the text is not the inner
type's: hex or byte arrays, `null`, a missing or mistyped inner member, an
inner integer out of range). For the map / set types: `accept` rows give
the entries in another order, `reject` rows repeat a key or an element (two
equal inner values are equal bytes).

## Name coders

`name-vectors.json` pins the two arithmetic name coders for every language
that has them: identifier names (`psio/name.hpp`: `name_to_number`,
`number_to_name`; `a`-`z`, `0`-`9`, `-`, at most 18 characters) and method
names (`psio/compress_name.hpp`: `method_to_number`, `number_to_method`,
`is_hash_name`). It is generated by `psio_name_conformance_emit`
(`cpp/tests/name_conformance_emit.cpp`); the ctest
`psio_name_conformance_regen` fails if the checked-in file is not what the
C++ headers generate. Regenerate with

```sh
<build>/cpp/tests/psio_name_conformance_emit conformance/name-vectors.json
```

```
{ "version": 1, "generator": "...",
  "names":   [ [text, method_number, method_text, name_number, name_text], ... ],
  "numbers": [ [number, method_text, name_text], ... ] }
```

Numbers are decimal strings. A `names` row gives both encoders applied to
`text` and each decoder applied to its encoder's result; a `numbers` row
gives both decoders applied to an arbitrary number. The rows are the format
of `rust/psio/tests/fixtures/compress-name-vectors.json`, and the first 92
names and the random ones (seed 12345) are that file's corpus, so the Rust
test can read this file instead.

The rules the rows pin:

- **A number is a name's only if it decodes to the name.** Both encoders
  decode what they encoded. `name_to_number` returns 0 when the result is
  not the text (a doubled hyphen — the model has no frequency for `-` after
  `-` —, or a code that needs more than 64 bits). `method_to_number` then
  takes the hash form instead (also when the code has bit 56 set, which
  marks a hash number), so `getSymbolType` is `#hmlnslheseoypnnp`, not the
  cut-off code that read back as `getsymboltyp`.
- **Method names compare in canonical form**: the coder ignores case and
  reads a digit or `_` as the letter of its symbol; `number_to_method`
  writes lower-case letters. The hash is of the bytes as written.
- **Hash text** is `#` and sixteen of the letters `eaiotnrslcuhdpmy` whose
  number has bit 56 set. Any other text that starts with `#` is 0 (it was
  2^64 − 1 or an arbitrary number).
- For every `n = method_to_number(s) != 0`:
  `method_to_number(number_to_method(n)) == n`. For every
  `n = name_to_number(s) != 0`: `number_to_name(n) == s`.

## Interfaces and method arguments

`interface-vectors.json` (described in `interface-vectors.md`; emitted by
`psio_interface_conformance_emit`, ctest `psio_interface_conformance_regen`)
pins the `Interface` / `Func` Schema IR of a method declaration — names,
parameter names and types, results, parameter bounds, `returns(...)`, the
argument cap and the parameter-count cap — and the bytes and text of
argument lists (a named object or a positional array, `docs/json.md`
"Method arguments") and of results.
